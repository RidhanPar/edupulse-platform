# Deploying EduPulse

This is the runbook for the first production deploy of the multi-tenant version, and for
deploys after it. Steps marked **(you)** need an account, a payment method or a decision,
so they cannot be automated from the repository.

## What gets created

| Piece | Where | Why |
|---|---|---|
| Web service `edupulse-platform`, Starter plan | Render, Frankfurt | Paid plans do not sleep, and support the pre deploy migration step |
| PostgreSQL 16 `edupulse-db` | Render, Frankfurt | Durable data. The free plan's disk is wiped on every deploy |
| Object storage bucket | AWS S3, `eu-central-1` (Frankfurt) | Uploaded datasets and trained models |

Everything sits in the EU. UK and EU institutions ask where student data is held before
anything else, and "Frankfurt, all of it" is a short answer.

Why AWS S3 for storage: it is the provider university procurement and security teams
already know, objects are encrypted at rest (the app also requests it explicitly on every
write), and access can be limited to one bucket with a short IAM policy. Cloudflare R2
also works with no code change if egress cost ever matters. Set `STORAGE_ENDPOINT` to its
endpoint instead.

## 1. Storage bucket (you)

1. Create a bucket in `eu-central-1`, for example `edupulse-prod-data`. Keep "Block all
   public access" on. Turn on versioning, so an overwritten model can be recovered.
2. Create an IAM user for the app with only this policy (no console access):

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Action": ["s3:PutObject", "s3:GetObject"],
       "Resource": "arn:aws:s3:::edupulse-prod-data/org/*"
     }]
   }
   ```

   There is no `DeleteObject`: the app never deletes objects yet. The retention purge job
   will need it when it is built.
3. Create an access key for that user and keep it for step 2.

## 2. Render (you)

1. In Render, choose New, Blueprint, connect `RidhanPar/edupulse-platform`, and pick the
   branch to deploy. Use `feat/multi-tenant` for a staging deploy first. The live demo on
   `main` is untouched by this.
2. Check the plan names Render shows match `render.yaml` (`starter`, `basic-256mb`). Render
   renames plans from time to time. This creates paid resources: confirm the prices shown.
3. Fill in the variables marked `sync: false`:
   `STORAGE_ENDPOINT` = `https://s3.eu-central-1.amazonaws.com`,
   `STORAGE_REGION` = `eu-central-1`, `STORAGE_BUCKET`, `STORAGE_ACCESS_KEY`,
   `STORAGE_SECRET_KEY`, and `APP_BASE_URL` = the service's URL.
   `FLASK_SECRET_KEY` and `MODEL_SIGNING_KEY` are generated by Render. Never copy one into
   the other.
4. Apply. The pre deploy step runs `flask db upgrade`. If a migration fails the deploy
   stops and nothing changes.

## 3. First boot checks

From the service's Shell tab:

```bash
python scripts/check_storage.py
```

It writes, reads and removes one test object and confirms the provider reports encryption
at rest. Then create the first organisation and owner:

```bash
flask --app wsgi create-org "Pilot College" owner@pilotcollege.ac.uk
```

It prints a one time invite link. Send it to the owner yourself.

## 4. Set the proxy hop count from evidence

The app trusts `PROXY_HOPS` proxies when it reads the client's address, which the login
rate limit and the audit log depend on. Do not guess the number.

1. The startup log shows `Trusting 1 proxy hop(s) ...`.
2. Open the site in a normal browser. The log then shows one line:
   `First request: X-Forwarded-For='...' has N entries, connecting peer=..., PROXY_HOPS=1`.
3. A browser sends no `X-Forwarded-For` of its own, so N is the number of proxies in front
   of the app. If N is not 1 (for example a CDN was added in front of Render), set
   `PROXY_HOPS` to N and redeploy. Too low and the limiter sees the proxy instead of the
   user. Too high and a client can forge their address.

## 5. Measure the audit page on the real database

Figures measured on a laptop with a warm cache must not appear in any document. Once the
owner has used the app for a while:

```bash
python scripts/explain_audit.py pilot-college
```

Only quote a timing from a run whose `Buffers:` line shows `read=` above zero, which means
it read from disk. Run it after the database has been idle, or after a restart from the
Render dashboard, to get one.

## 6. Cut over

When staging has been checked end to end: merge `feat/multi-tenant` into `main`, point the
production blueprint at `main`, move the custom domain if there is one, then retire the
old free service. Its disk holds only the old shared demo data.

## Known limits to fix before real student data

These are why the README still says synthetic or anonymised data only.

- No retention job yet. Expired datasets are marked but not purged, and audit IP
  addresses are not yet nulled after 90 days on a schedule.
- The app connects as the database owner, so a determined operator could disable the
  audit trigger. Next step: a separate login role for the app that cannot alter tables.
- One web worker, because the login rate limit lives in process memory. Move it to Redis
  before adding workers.
- Training runs inside the web request (gunicorn timeout 120 s). Large files need a
  background job.
- No signed Data Processing Agreement, DPIA, breach procedure or penetration test yet.
